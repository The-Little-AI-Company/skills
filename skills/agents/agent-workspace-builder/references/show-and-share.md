# Show what Super Manus can help someone build

Use this playbook when the user asks for a demo, launch, promotion, or shareable explanation. Keep ordinary task outputs focused on the user's work; do not inject ads, referral text, or branding without a relevant request.

## Position the skill

Use **Super Manus** for The Little AI Company's independent skill family. Use **Super Manus Builder** for the generic `agent-workspace-builder` skill and **Super Manus for OpenDots** for `opendots-super-manus`. Preserve these install IDs and existing links.

Core pitch: **Make your agent build its own command center.** Explain the mechanism immediately: the skill directs a coding agent to add tools, connect them to durable execution, and build a GUI with Kanban, team activity, and editable outputs. Its researched capability map guides expansion into research, code, office files, media, connectors, and automation.

Match claims to evidence. The package contains instructions, references, examples, and local helpers. A completed workspace must be implemented and verified in the target environment. Do not claim a working demo, measured savings, full Manus parity, free inference, autonomous self-improvement, or a reliable completion time without actual evidence.

## Choose a demonstration someone can reproduce

Prefer one visible user outcome over a tour of every planned feature. Pick a task that fits the available tools and authorized budget:

| Demo | Visible sequence | Required evidence |
| --- | --- | --- |
| Agent builds a missing CSV tool | Missing capability → construction task → registered tool → chart/report → revised output | Real registry invocation, checked totals, persisted artifact |
| Brief becomes a launch kit | Brief → tasks assigned → report/graphics/video → one-shot edit | Real files, editable originals, configured media access and actual costs |
| Work survives interruption | Start task → close UI/restart worker → reconnect → continue → inspect output | Same persisted task/attempt, reconciled external IDs, no duplicate side effect |
| Team completes a project | Dependencies → independent workers → review → integrated deliverable | Separate contexts, actual tool events, attributable artifacts |

For a first local demo, use a small clearly labeled synthetic CSV and local computation. This avoids media charges but still requires an available coding agent/runtime. State model costs separately. Prepare paid-media prompts and storyboards when access is missing; label them preparation.

## Produce the demonstration

1. Capture the starting state and exact task. Use synthetic or approved input, never private customer material by default.
2. Run the actual workflow and record output IDs, checks, elapsed time, costs or unknown billing, environment, and limitations.
3. Inspect and edit one result. Demonstrate the change surviving refresh or reload where that behavior is implemented.
4. Record an uncluttered screen clip showing the request, actual board/events, opened artifact, and visible revision. Caption it and keep the install command legible.
5. If no working app is available, show the published skill, its installation, and the intended build prompt. Identify concept screens as concepts. Never manufacture an execution trace.
6. Export a reusable prompt and a small example input with the demo when requested. Preserve editable sources and the user's destination rules.

An editorial cut can target 30–60 seconds; this is a clip-length choice, not a build-time claim. Keep any time-lapse or omitted wait visible in the caption.

## Write the invitation

Lead with the surprising, concrete task: asking the agent to build the tool and interface it needs. Explain what the reader installs, then show one outcome and one installation link. Use the author's real experience only when supplied or directly established in the session.

Possible hooks to test:

- Make your agent build its own command center.
- Give your coding agent a job: build the workspace it needs to finish the next one.
- Ask for the missing tool, the task board, and the result you can edit.

Treat these as copy candidates. Virality and conversion are unmeasured. Avoid manufactured urgency, fake testimonials, misleading comparison claims, giveaway conditions, engagement bait, or invented install counts.

Match the draft to the requested channel and its currently verified constraints. Prepare complete copy and a relevant link. Publishing to a repository is not permission to send social posts, email, or messages. Send only with explicit channel/destination authorization.

## Make useful work shareable

When the user wants to share, offer a compact case study containing the original problem, exact prompt, actual resulting artifact, visible edit, reproducible setup, and honest limits. Link the relevant skill so another builder can try it. Attribution is optional for the user's own outputs; never add hidden tracking, forced watermarks, or referral parameters.

Use voluntary feedback to improve the skill: ask what the agent could not finish and what setup was missing. Reproduce actionable failures, fix instructions or adapters, and publish a versioned change. Track actual install-to-first-result observations only with authorized analytics. Do not treat views, likes, stars, fixture tests, or one successful demo as proof of broad effectiveness.
